# F4 — Federated MAE on BDD100K with clients split by driving condition

[F3](F3.md) found no non-IID penalty under Dirichlet label skew on CIFAR-100. A label-free objective only sees label
skew through the images each client gets, and those stayed broadly similar. F4 tries the stronger kind of skew F3
pointed to: **BDD100K, with each client holding different driving conditions** (one client clear daytime, another clear
night, another snow and rain). The images themselves now differ between clients, which is the axis SSL responds to.

F4 asks three questions, starting from a warm-started MAE:

1. Does a federated pass improve the representation, scored on BDD's test split?
1. Does splitting clients by condition cost anything, compared with clients that each see a fair mix (IID)?
1. Do FedProx or FedAdam improve on FedAvg under this split?

The headline runs use three seeds.

## Setup

**Data.** BDD100K train split (`data=bdd_fl`), resized to 64px. Images with an undefined time of day, weather or scene
are dropped, and only the three well-populated scenes are kept (`min_canary_count=500`: city street, highway,
residential). That leaves 61,239 images. The label the probes predict is the **scene**. Clients are split on a different
axis (weather and time of day), so the probe reads something the split does not sort by. City street is 61–62% of both
the train and test images.

**Condition partition** (`partition.scheme=condition`, new in F4). Images are lined up so that similar conditions sit
next to each other: weather first (clear → partly cloudy → overcast → rainy → snowy → foggy), then time of day within
each weather. The line is cut into `num_clients` equal blocks. A client whose condition runs out is filled up with the
next most similar one, and a large condition spans several clients. Each client's mix is logged at startup. At 5
clients, roughly:

| Client | Mix |
| -- | -- |
| 0 | clear daytime (100%) |
| 1 | clear night (83%), clear dawn/dusk (16%) |
| 2 | clear night (100%) |
| 3 | overcast daytime (58%), partly cloudy daytime (35%), partly cloudy dawn/dusk (5%) |
| 4 | snowy and rainy, day and night (about 80%), plus a dozen rarer combinations |

Clear weather is about 60% of BDD, so three of five clients are clear-weather clients. The IID control
(`partition.scheme=iid`) splits the same pool uniformly at random.

**Global hold-out.** Before partitioning, 203 images per *(weather, scene)* pair are held out for the per-round health
check (`global_holdout_strata=weather`, the `auto` default under the condition split). That is enough for 100 support
and 100 query images per scene. The three fog pairs are too small and are skipped, so the hold-out is 3,045 images and
each client gets about 11.6k. The IID control uses the same weather-balanced hold-out, so each IID run holds out exactly
the same images as the condition run with the same seed.

**Model and training.** The tiny ViT (`patch_size=8`, `embed_dim=96`, `depth=4`, `num_heads=3`) with the default MAE
decoder (`decoder_dim=64`, `decoder_depth=2`, `mask_ratio=0.75`, `norm_pix_loss=true`). Batch 32, AdamW at `lr=1e-3`. 5
clients, `steps_per_round=5`, one pass (`client_epochs=1`), which gives 73–74 rounds. Within each client the stream
follows the default `class_blocked` order (see *Caveats*).

**Warm start.** A full-method MAE well from `warm_well.py` (encoder and decoder), trained on the same BDD train split at
64px until its loss plateaued. The well therefore saw every image the clients train on, as in F2–F3.

**Readouts.**

- *Per round:* the health monitor on the global hold-out (100 support and 100 query images per scene, so 300 query
    images). Label-free geometry (RankMe, drift), kNN and linear probes, and per-client divergence.
- *Once, before and after training:* the **final evaluation**. kNN (k=20) and linear probes are fitted on 3,000 training
    images per scene and scored on BDD's 17,478-image test split, which no client sees. `gain = final − start`.
- **Balanced accuracy** (new in F4). Each probe reports plain accuracy and *balanced* accuracy, the mean of the
    per-scene accuracies. Plain accuracy on a test split that is 61% city street rewards predicting city street.
    Balanced accuracy puts chance at 1/3 however skewed the labels are. F4 reads its results off the balanced scores.

## Findings

### FedAvg gains a small but reliable two points

Gains on the test split, in accuracy points, mean ± standard deviation over seeds 0–2:

| Strategy (condition split) | kNN balanced | Linear balanced | kNN plain | Linear plain |
| -- | -- | -- | -- | -- |
| **FedAvg** | **+2.1 ± 0.2** | **+1.9 ± 0.7** | +2.5 ± 0.2 | +0.2 ± 0.5 |
| FedProx (μ=0.01) | +1.4 ± 0.3 | +0.9 ± 0.4 | +1.8 ± 0.6 | +0.1 ± 0.6 |
| FedAdam (server `lr=1e-3`) | +0.5 ± 0.2 | +0.2 ± 0.2 | +0.9 ± 0.8 | −0.4 ± 0.6 |
| FedAdam (server `lr=1e-2`) | −0.5 ± 0.8 | −0.3 ± 1.4 | −0.2 ± 1.3 | −2.2 ± 1.8 |

The starting model sits at 0.43–0.44 balanced kNN and 0.47–0.48 balanced linear, with chance at 0.33. FedAvg's balanced
gains are positive in all three seeds on both probes, and its kNN gain varies by only ±0.2 between seeds. The
improvement is small, but it is not noise.

Seed 0 reproduces an earlier unseeded run to four decimals, so training on the GPU is deterministic here.

### Splitting clients by condition costs nothing

FedAvg under the condition split against FedAvg with IID clients. Same seeds, same hold-out, same everything except how
images are dealt to clients:

| Gain on test (balanced) | Condition split | IID | IID − condition, per seed |
| -- | -- | -- | -- |
| kNN | +2.1 ± 0.2 | +2.2 ± 0.2 | +0.1, +0.1, +0.1 |
| Linear | +1.9 ± 0.7 | +1.6 ± 0.4 | +0.4, −0.4, −1.0 |

The two partitions end at the same score. On kNN, IID is ahead by exactly 0.1 in every seed. On linear, the sign changes
between seeds. Any cost of the condition split is under half a point.

The clients do behave differently. Under the condition split, client models move about twice as far from each other per
round (mean cross-client CKA distance 0.025–0.034, against 0.014–0.018 under IID). Averaging removes that difference:
the global models' RankMe (about 10 in both) and drift (at most 0.21 in both) also match.

The likely reason is that this setup is too gentle for the split to matter. The well already knows every condition. Each
client trains only 5 steps between averages. And the global model barely leaves the well: its drift stays at or below
about 0.2 on a 0-to-1 scale. With so little local training, the clients cannot get far enough apart to hurt the average.
This explanation is untested; more local steps per round is the direct test (see *Open follow-ups*).

### FedAvg beats FedProx and FedAdam in every seed

Per-seed differences from FedAvg (balanced accuracy, seeds 0 / 1 / 2):

|  | kNN | Linear |
| -- | -- | -- |
| FedProx μ=0.01 − FedAvg | −0.7, −0.5, −1.0 | −0.3, −1.0, −1.6 |
| FedAdam `lr=1e-3` − FedAvg | −1.5, −1.4, −1.8 | −1.1, −2.0, −2.1 |

**FedProx** penalizes a client for moving away from the global model. Since there is no non-IID cost to correct, the
penalty only slows learning, as in F3. A stronger penalty (μ=0.1, one seed, from an earlier batch with a smaller
hold-out) gained less on kNN than μ=0.01 in the same batch (+0.9 against +1.6, plain accuracy) and about the same on
linear (+0.9 against +0.8).

**FedAdam** depends on its server step size:

- At the default `lr=1e-2` the server throws the model far from the well within the first rounds (drift 0.83–0.87,
    against at most 0.21 for FedAvg), and the gain is about zero with large seed-to-seed variation. RankMe never grows:
    it ends at 1.5 in seed 0 and at 2.3–2.9 in seeds 1–2.
- At `lr=1e-3` it is stable (drift 0.14–0.22, seeds agree to ±0.2) but learns too little. RankMe grows only to about
    4.3, where FedAvg reaches about 10.

A value in between (e.g. `3e-3`) could still close part of the gap. Nothing here suggests FedAdam would overtake FedAvg.

**FedYogi** (seed 0 only, `lr=1e-2`) shows why the balanced score matters. Its plain kNN accuracy rose by 2.6 points,
level with FedAvg, but its balanced kNN accuracy *fell* by 2.3. The plain gain came from predicting city street more
often while getting worse at highway and residential. FedYogi was dropped from the seeded sweep.

### The representation spreads out under FedAvg

RankMe (how many dimensions the representation uses) starts at about 3 out of 96. Under FedAvg it rises to about 10 in
every seed, fastest toward the end of the pass. FedProx reaches 7–8. FedAdam at `lr=1e-3` reaches about 4. The order
matches the order of the test gains.

### The per-round probes cannot see gains this small

With 300 query images, per-round accuracy moves in steps of 0.3 points, and FedAvg's kNN changes by about 1.4 points
from one round to the next. That is readable, but it shows no consistent trend: over the pass, FedAvg's per-round kNN
rises in one seed, falls in another and stays flat in the third. A 2-point gain is below what probes fitted on 100
examples per scene can resolve. The final evaluation, fitted on 3,000 per scene, does resolve it. For the per-round
curves, RankMe and drift are the informative signals.

### Exploratory runs: passes, client count and SimSiam

Before the seeded runs, single-seed runs explored the setup. They predate balanced accuracy and the larger hold-out:
their final evaluation used every training image as probe support (plain accuracy, which starts at 0.62 against the 0.61
majority share), and their per-round probes scored only 15 images. Gains in plain accuracy:

| Run (FedAvg, seed 0) | kNN | Linear | RankMe |
| -- | -- | -- | -- |
| MAE, 4 clients, 1 pass | +1.3 | +1.2 | 2.5 → 6.3 |
| MAE, 4 clients, 5 passes | +2.4 | +2.2 | 2.5 → 8.4 |
| MAE, 10 clients, 1 pass | +0.5 | +0.2 | 2.3 → 3.6 |
| MAE, 10 clients, 5 passes | +1.1 | +1.2 | 2.3 → 8.9 |
| SimSiam, 4 clients, 1 pass | +0.3 | +0.2 | 2.1 → 2.0 |
| SimSiam, 4 clients, 5 passes | −0.2 | +0.5 | 2.1 → 1.8 |

They suggest three things, none of them seeded:

- **More passes help MAE**, roughly doubling the gain, as in F3.
- **More clients learn less per pass.** Each client's data is smaller and more uniform, and there are fewer rounds (39
    at 10 clients against 96 at 4).
- **SimSiam holds its well but does not improve on it**, and its RankMe shrinks slightly. Its well started at the same
    level as the MAE well (0.623 against 0.618 plain kNN), so this is about the federated continuation, not about
    SimSiam on BDD in general. SimSiam ran at untuned defaults.

## Caveats

- **The starting model is weak.** It uses about 3 of 96 dimensions and reaches 0.43 balanced kNN with chance at 0.33.
    Gains of two points may be all that a federated pass can add to a well this weak. A stronger well could show larger
    effects, including a non-IID cost.
- **The well saw all the training data,** including the per-round hold-out. The per-round curves therefore start from a
    model that already trained on the images they score. The final evaluation scores the test split and is not affected.
- **Within-client order is `class_blocked`.** Each client streams all its city-street images first, then highway, then
    residential, and all clients are on the same scene at the same time. Every arm shares this, so the comparisons are
    fair, but it adds a synchronized drift over the pass that `stream=iid` (used in F3) would not. Results under
    `stream=iid` may differ.
- **Three seeds** for FedAvg, FedProx (μ=0.01), FedAdam and the IID control. FedProx μ=0.1, FedYogi and all exploratory
    runs are seed 0 only.
- **Server and client hyperparameters are untuned** for BDD. FedAdam's result describes `lr=1e-2` and `1e-3`, not the
    method.

## How to run

```bash
BDD=/abs/path/to/bdd100k     # images/100k/<split>/*.jpg + labels/<split>/*.json

# 1. The MAE well (encoder + decoder), on the BDD train split at 64px
uv run python scripts/warm_well.py data=bdd data.split=train data.min_canary_count=50 bdd_root=$BDD \
  device=cuda img_size=64 stream.support_per_canary=25 stream.query_per_canary=25 \
  backbone=mae well_out=wells/bdd_mae_well.pt

# Shared settings of the federated runs
COMMON="data=bdd_fl data.source.bdd_root=$BDD ssl=mae img_size=64 device=cuda \
  init=pretrained init.checkpoint=$PWD/wells/bdd_mae_well.pt \
  num_clients=5 client_epochs=1 support_per_class=100 query_per_class=100 \
  final_eval.enabled=true final_eval.support_per_class=3000 \
  ~final_eval.test_overrides.split +final_eval.test_overrides.source.split=test \
  hydra.sweep.dir=outputs/bdd_fl/5_clients/1epoch_q100"

# 2. FedAvg and FedProx, condition split
uv run python scripts/run_federated.py -m $COMMON partition.scheme=condition seed=0,1,2 strategy=fedavg,fedprox \
  'hydra.sweep.subdir=${hydra:runtime.choices.strategy}/seed${seed}'

# 3. FedAdam with the smaller server step
uv run python scripts/run_federated.py -m $COMMON partition.scheme=condition seed=0,1,2 strategy=fedadam \
  strategy.server_optimizer.lr=1e-3 'hydra.sweep.subdir=fedadam/seed${seed}'

# 4. IID control, same weather-balanced hold-out
uv run python scripts/run_federated.py -m $COMMON partition.scheme=iid global_holdout_strata=weather \
  seed=0,1,2 strategy=fedavg 'hydra.sweep.subdir=iid/fedavg/seed${seed}'
```

Memory: every image is decoded into RAM, about 3 GB for the train split at 64px plus 0.9 GB for the test split.

## Open follow-ups

- **When does the condition split start to matter?** Rerun FedAvg condition vs IID with more local training per round
    (`steps_per_round=50` or `100`). If a gap appears, that is the regime where FedProx gets a fair test.
- **A stronger well**: a longer warm-up or larger images, so a federated pass has more to work with.
- **`stream=iid` within clients**, to remove the synchronized scene order.
- **More clients** (about 12): only then do snow and rain each get a client of their own.
- **FedAdam at `lr=3e-3`**, and SimSiam under the seeded protocol.
