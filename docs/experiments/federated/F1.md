# F1 — Federated harness parity

The first FL sub-study (see the [federated track overview](index.md)). Before any non-IID or aggregation-skew
question is worth asking, the harness itself needs to reproduce the centralized reference it wraps
([P0.1](../phase0/P0.1.md)'s `from_scratch` tables) under degenerate settings where FedAvg either does nothing or
should behave like one continuous model. This is the FL analogue of P0.1's own "does the loop run end-to-end" check —
infrastructure validation, not a scientific result.

Both `C`-factor backbones from P0.1 are covered, not just MAE: SimSiam is the collapse-*capable* method (predictor +
stop-gradient), so it's the sharper check of whether FedAvg's periodic weight-averaging interacts badly with a method
that already sits closer to a collapse failure mode — a question MAE's reconstruction objective can't raise.

## Two variants, two different bars

The two runs below check different things and should be read differently:

1. **`num_clients=1` — exact reproduction, but only for the loss series.** FedAvg over a single client is a no-op
    (averaging one thing is that thing), and `partition_source` degenerates to the original image order for either
    scheme at `num_clients=1` (checked in `cafl4ds/federated/partition.py`), so the client trains on bit-identical
    data, in the same order, from the same seed, through the *same* `StreamingLoop.train_step` code path centralized
    uses. So the **per-step loss** in the client's `run_log.jsonl` should match the centralized loss series closely.
    **The health series does not line up automatically — this is a harness quirk, not noise to average away:**
    `train_step` never calls the monitor itself; health is only logged inside `StreamingLoop.run()`'s own
    `step % eval_every == 0` gate ([loop.py](../../../cafl4ds/loop.py)). The federated client is driven by
    `train_round`, which calls `train_step` directly and never `run()` — so `eval_every` has **no effect** on the
    federated path. The only health reading federated does is the orchestrator's own once-per-`steps_per_round`
    measurement of the aggregated model, logged under the **round index** (not the true step count) with `era`
    always `-1` (never the true era). So: match `steps_per_round` to the cadence you want checkpoints at, and
    multiply the logged round index by `steps_per_round` to get the comparable true step — don't expect the raw
    `step`/`era` columns to align, and don't expect a forced final-step reading the way `run()`'s `_finalize` gives
    the centralized log. If the loss series matches but health checkpoints look sparse/misaligned, that's expected;
    if the loss series itself diverges, the bug is in the federated wiring (partitioning, weight broadcast, the round
    loop), not in FedAvg as an algorithm.
2. **`partition.scheme=iid`, several clients — sanity check, not exact match.** Splitting the *same* IID data across
    several clients and periodically averaging their weights is **not** mathematically identical to one continuous
    model, even with no heterogeneity: each client takes several local steps between averages, so the trajectory is a
    genuine (if mild) approximation. The bar here is qualitative — loss should still decrease, RankMe should still
    respond to the stream, nothing should diverge or NaN — not that the numbers land on the centralized table.

## How to run

Centralized reference (already established, [P0.1](../phase0/P0.1.md)):

```bash
uv run python scripts/run_loop.py ssl=mae eval_every=4 data_root=data/stl10
uv run python scripts/run_loop.py ssl=simsiam eval_every=4 data_root=data/stl10
```

**Variant A — `num_clients=1`, exact-match settings** (mirrors the centralized run's data budget and reservations
exactly, so the two loss series should be directly comparable; `steps_per_round=4` matches the centralized
`eval_every=4` cadence for the health checkpoints — note `eval_every` itself does nothing here, see above):

```bash
uv run python scripts/run_federated.py ssl=mae init=from_scratch num_clients=1 partition.scheme=iid \
    steps_per_round=4 data_root=data/stl10 \
    max_per_class=120 max_train_per_class=80 \
    support_per_class=20 query_per_class=20 era_eval_per_class=10
    

uv run python scripts/run_federated.py ssl=simsiam init=from_scratch num_clients=1 partition.scheme=iid \
    steps_per_round=4 data_root=data/stl10 \
    max_per_class=120 max_train_per_class=80 \
    support_per_class=20 query_per_class=20 era_eval_per_class=10
```

**Variant B — `partition.scheme=iid`, 8 clients** (uses `federated.yaml`'s own multi-client data budget —
`max_per_class=500`, `support_per_class=5`, `query_per_class=5`, `era_eval_per_class=2` — sized for a shard rather
than the full centralized dataset; do not expect it to reproduce the centralized numbers, see above):

```bash
uv run python scripts/run_federated.py ssl=mae init=from_scratch num_clients=8 partition.scheme=iid \
    data_root=data/stl10

uv run python scripts/run_federated.py ssl=simsiam init=from_scratch num_clients=8 partition.scheme=iid \
    data_root=data/stl10
```

## What to compare

Each run writes `run_log.jsonl` (centralized: one file; federated: one per client plus `global_*run_log.jsonl` for
the aggregated model) to its Hydra run dir. Read the logs back with `cafl4ds.run_log.read_run` / `tabulate` (as in
[P0.1](../phase0/P0.1.md#how-to-run)):

- **Variant A — loss.** Diff the **client's** `loss` series (per training step, real step/era) against the matching
    centralized table (`mae_from_scratch` or `simsiam_from_scratch`) — this is the row-for-row comparison. A
    material mismatch points at the federated wiring (partitioning, weight broadcast, the round loop), not at FedAvg.
- **Variant A — health.** Diff the **global** log's `health` series against the same centralized table, but only
    after multiplying its round index by `steps_per_round` to get the comparable step — don't expect an exact
    checkpoint-count match (a trailing partial round may not get a forced final reading the way the centralized
    `run()` guarantees one). For SimSiam in particular, also sanity-check the loss floor doesn't ride to the −1
    constant-solution collapse fingerprint from [P0.2.0](../phase0/P0.2.0.md) — that would mean the federated wiring
    itself is inducing collapse, not just reproducing the centralized run.
- **Variant B**: no fixed target — just confirm the global model's loss decreases and RankMe responds to the stream
    the same *qualitatively* as every P0.1 configuration did, with nothing non-finite, for both backbones.

## Result — Variant A (CPU)

`num_clients=1`, `partition.scheme=iid`, `steps_per_round=4`, both backbones, exact-match settings above. The
client's stream exhausts after 30 steps (round 7 only pulls the last 2), so round 7 lands on total-steps-trained =
30 — exactly the centralized run's forced final reading at step 29.

**Loss: bit-identical at every step, both backbones.** `client0`'s per-step loss/grad-norm series matches the
centralized `mae_from_scratch`/`simsiam_from_scratch` series exactly, step for step. This is the strongest possible
confirmation that partitioning, weight broadcast, and the round loop don't perturb `train_step` at `num_clients=1`.

**Health at the final checkpoint (round 7 vs. centralized step 29) — exact, except drift:**

| metric | mae (centralized / federated) | simsiam (centralized / federated) |
| -- | -- | -- |
| rankme | 2.414769 / 2.414769 | 3.585857 / 3.585857 |
| rankme_proj | — | 11.648937 / 11.648937 |
| mean_feature_var | 3.6952e-05 / 3.6952e-05 | 3.6611e-04 / 3.6611e-04 |
| offdiag_cov | 7.4483e-08 / 7.4483e-08 | 1.0027e-05 / 1.0027e-05 |
| uniformity | −0.014057 / −0.014057 | −0.125902 / −0.125902 |
| alignment_proj | — | 0.918999 / 0.918999 |
| knn_acc | 0.155 / 0.155 | 0.125 / 0.125 |
| linear_acc | 0.235 / 0.235 | 0.215 / 0.215 |
| **cka_drift** | **0.050151 / 0.013216** | **0.100785 / 0.094579** |
| **cosine_drift** | **0.470868 / 0.140025** | **0.290520 / 0.148886** |

Every metric that reads the *current* embedding matches to the last printed digit. Only drift diverges, and the
reason is mechanical, not a training discrepancy: drift is read against a **reference checkpoint**, and the two
harnesses capture that reference at different points. Centralized takes its reference at the very first health log
— true step 0, after **1** training step. Federated's `global_monitor` is only invoked once per round, so its
reference is captured at round 0 — after **4** training steps already ran. Comparing against an already-somewhat-
adapted reference systematically understates drift, which is exactly the pattern above (federated drift smaller at
every comparable point, both backbones). **Conclusion: drift readings are not comparable between the centralized and
federated harnesses at this cadence — everything else is.**

**Intermediate rounds are close but not exact, and this is now precisely explained, not just "noisy":** round `r`'s
health reflects the model after `4(r+1)` total training steps, while centralized's `eval_every=4` schedule logs
after `s+1` steps at `s ∈ {0, 4, 8, ...}`. Those two schedules sit one training step apart at every checkpoint except
the last, where the stream's exhaustion (30 steps, divisible by neither schedule's stride in a way that would
otherwise misalign them) happens to line the two up exactly.

**Minor harness observation (not yet acted on):** the federated global log's `"run"` field is always the literal
string `"global"`, with no method/config info — unlike the centralized run's `"run": "mae_from_scratch"` — making
the two harder to tell apart when comparing raw log lines across backbones. Worth a small logging fix later
(`scripts/run_federated.py`'s `RunLogger(..., run_name="global")` call), not addressed here.

**Verdict: F1 Variant A passes.** The federated harness reproduces the centralized reference exactly at
`num_clients=1`, for both backbones, on every metric except drift — and the drift gap is fully explained by a
reference-checkpoint timing difference rather than by any divergence in training. Variant B (multi-client IID) is
still pending.
