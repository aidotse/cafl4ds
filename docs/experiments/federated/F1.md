# F1 — Federated harness parity

The first FL sub-study (see the [federated track overview](index.md)). Before any non-IID or aggregation-skew
question is worth asking, the harness itself needs to reproduce the centralized reference it wraps
([P0.1](../phase0/P0.1.md)'s `from_scratch` tables) under degenerate settings where FedAvg either does nothing or
should behave like one continuous model. This is the FL analogue of P0.1's own "does the loop run end-to-end" check —
infrastructure validation, not a scientific result. Both `C`-factor backbones are covered: SimSiam is the
collapse-*capable* method, so it's the sharper check of whether periodic weight-averaging interacts badly with a
method already closer to a collapse failure mode — a question MAE's reconstruction objective can't raise.

## Two variants, two different bars

- **`num_clients=1` — exact reproduction.** FedAvg over one client is a no-op, and `partition_source` degenerates to
    the original image order at `num_clients=1` for either scheme, so the client trains on identical data, same
    order, same seed, through the same `train_step` code path centralized uses. Loss should match exactly.
- **`partition.scheme=iid`, several clients — sanity check, not exact match.** Averaging several separately-trained
    clients isn't identical to one continuous model even with no heterogeneity. The bar is qualitative: loss
    decreases, RankMe responds to the stream, nothing diverges or NaNs.

**A harness quirk that affects reading health, not training itself:** the federated client calls `train_step`
directly (never `StreamingLoop.run()`), so `eval_every` has no effect on the federated path. Health is instead read
once per round by the orchestrator, tagged by **round index** (not the true step count) with `era` always `-1`. Set
`steps_per_round` to the cadence you want, and multiply the round index by it to get the comparable true step.

## How to run

```bash
# Centralized reference (P0.1):
uv run python scripts/run_loop.py ssl=mae eval_every=4 data_root=data/stl10
uv run python scripts/run_loop.py ssl=simsiam eval_every=4 data_root=data/stl10

# Variant A — num_clients=1, exact-match settings (steps_per_round=4 mirrors eval_every=4):
uv run python scripts/run_federated.py ssl=mae init=from_scratch num_clients=1 partition.scheme=iid \
    steps_per_round=4 data_root=data/stl10 \
    max_per_class=120 max_train_per_class=80 \
    support_per_class=20 query_per_class=20 era_eval_per_class=10
uv run python scripts/run_federated.py ssl=simsiam init=from_scratch num_clients=1 partition.scheme=iid \
    steps_per_round=4 data_root=data/stl10 \
    max_per_class=120 max_train_per_class=80 \
    support_per_class=20 query_per_class=20 era_eval_per_class=10

# Variant B — partition.scheme=iid, 8 clients (federated.yaml's own multi-client data budget):
uv run python scripts/run_federated.py ssl=mae init=from_scratch num_clients=8 partition.scheme=iid \
    data_root=data/stl10
uv run python scripts/run_federated.py ssl=simsiam init=from_scratch num_clients=8 partition.scheme=iid \
    data_root=data/stl10
```

Each run writes `run_log.jsonl` (federated: one per client plus `global_*run_log.jsonl` for the aggregated model) to
its Hydra run dir; read back with `cafl4ds.run_log.read_run`/`tabulate` as in [P0.1](../phase0/P0.1.md#how-to-run).

## Result — Variant A (CPU)

`num_clients=1`, `steps_per_round=4`, exact-match settings, both backbones. The stream exhausts at 30 steps (round 7
pulls the last 2), landing exactly on the centralized run's forced final reading at step 29.

**Loss: bit-identical at every step, both backbones.** `client0`'s per-step loss/grad-norm matches the centralized
series exactly — the strongest possible confirmation that partitioning, weight broadcast, and the round loop don't
perturb `train_step` at `num_clients=1`.

**Health at the final checkpoint (round 7 vs. centralized step 29) — exact, except drift:**

| metric | mae (centralized / federated) | simsiam (centralized / federated) |
| -- | -- | -- |
| rankme | 2.414769 / 2.414769 | 3.585857 / 3.585857 |
| rankme_proj | — | 11.648937 / 11.648937 |
| mean_feature_var | 3.6952e-05 / 3.6952e-05 | 3.6611e-04 / 3.6611e-04 |
| offdiag_cov | 7.4483e-08 / 7.4483e-08 | 1.0027e-05 / 1.0027e-05 |
| uniformity | −0.014057 / −0.014057 | −0.125902 / −0.125902 |
| alignment_proj | — | 0.918999 / 0.918999 |
| knn_acc | 0.155 / 0.155 | 0.125 / 0.125 |
| linear_acc | 0.235 / 0.235 | 0.215 / 0.215 |
| **cka_drift** | **0.050151 / 0.013216** | **0.100785 / 0.094579** |
| **cosine_drift** | **0.470868 / 0.140025** | **0.290520 / 0.148886** |

Every metric reading the *current* embedding matches to the last printed digit. Only drift diverges, for a
mechanical reason: drift is read against a reference checkpoint, and the two harnesses capture it at different
points. Centralized takes its reference at true step 0 (after 1 training step); federated's `global_monitor` is
only invoked once per round, so its reference is captured at round 0 (after 4 steps). Comparing against an
already-adapted reference systematically understates drift — **drift readings aren't comparable between the two
harnesses at this cadence; everything else is.** Intermediate (non-final) rounds are close but not exact for the
same reason the schedules are offset by one training step at every checkpoint but the last.

**Two harness fixes came out of this run (both applied):**

- Log `"run"` field now carries method/init info (`global_mae_from_scratch`, `client0_simsiam_from_scratch`)
    instead of the bare `"global"`/`"client{id}"`, matching the centralized convention.
- The global health log's `"loss"` was always `null` (nothing ever called `log_loss` on that logger).
    `FederatedOrchestrator._record_round` now logs the round's sample-weighted mean loss across participating
    clients (the same weighting FedAvg uses to aggregate weights) before the health reading.

**Verdict: passes.** Exact reproduction at `num_clients=1`, both backbones, on every metric except drift — fully
explained by the reference-checkpoint timing difference, not a training divergence.

## Result — Variant B (CPU)

`num_clients=8`, `partition.scheme=iid`, `federated.yaml`'s default multi-client data budget, both backbones. Both
runs exhaust after 5 rounds.

**SimSiam — clean pass.** Loss decreases monotonically every round (−0.080 → −0.595; more negative is the correct
direction for `−cosine_similarity`). RankMe declines smoothly at both surfaces and stays far from
[P0.2.0](../phase0/P0.2.0.md)'s forced-collapse floor (loss ≤ −0.9, RankMe ~1.8) — healthy adaptation, same range as
P0.1's own `simsiam_from_scratch`. All values finite.

**MAE — clean pass, with a genuine client-drift fingerprint.** RankMe declines and levels off (3.21 → 2.20), same
shape as the centralized reference. Loss mostly decreases but ticks up once (0.957 → 1.059) before dropping again —
the first place in this exercise where FedAvg's actual weight-averaging shows a fingerprint `num_clients=1`
structurally can't produce: 8 separately-initialized clients trained on their own local batches then averaged can
land slightly off a smooth curve. Expected client drift, not a bug — and worth remembering once the non-IID sweep
starts, since this is the wobble the *IID* control already produces on its own.

**Verdict: passes.** Both backbones adapt sensibly under real multi-client FedAvg (the code path `num_clients=1`
never exercises); the one non-monotonic tick is a mechanistically-understood client-drift effect.

## Open follow-up (not acted on)

The global health read-out's probe (`knn_acc`/`linear_acc`) inherits the same small `support_per_class`/
`query_per_class` sized for a thin per-client shard, even though the global stream is built from the full,
unpartitioned dataset and isn't actually shard-constrained. Decoupling the global probe's reservation from the
per-client one (a new config knob) would give a less noisy global read, and matters more once Dirichlet skew makes
per-client shards small. Not done — noted for whenever a fairer federated-vs-centralized probe comparison is needed.
