# Why does adapting MAE lose to the frozen floor? A recipe diagnosis `[engineering + new runs]` (P1.2.2)

**What this substudy is.** The third P1.2 sub-study (see the [Phase 1 overview](index.md)), triggered by MAE's FAIL in
[P1.2.1](P1.2.1.md). After one pass over ~56,000 new BDD frames, the adapted MAE encoder reads below the frozen,
off-the-shelf encoder (**B5**) on every rung of both readout tasks (scene few-shot Δ −0.051). P1.2.2 asks whether that
is a property of continued MAE training on this data, or of the recipe used to do it. Its design was fixed in P1.2.1
before any P1.2.1 data was read, with one addition made after (marked below).

**Verdict of the pre-registered confirmation: FAIL.** The diagnosis named the culprit: P1.2.1's decoder (64-d × 2
blocks) is too small for a ViT-B encoder. With the MAE paper's 512-d × 8 decoder and the fine-tuning protections,
adapted MAE no longer loses to B5: the primary rung's gap closes from −0.051 to +0.003. But it does not gain either.
Against P1.2.1's bars as written, every rung on both tasks rules out a 2-point gain (the largest upper bound is +0.012),
which is a FAIL. The design mapped a FAIL to a No-Go for MAE and handed the decision to the user. The user has asked for
a second MAE pass first, building on the decoder finding, before any P1.3 decision.

| Recipe | Scene few-shot (*k* = 100) Δ vs B5 | Traffic light few-shot (*k* = 100) Δ vs B5 | Verdict |
| -- | -- | -- | -- |
| P1.2.1's (64-d × 2 decoder, lr 1e-4) | −0.051 [−0.067, −0.038] | −0.016 [−0.027, −0.005] | FAIL |
| **P1.2.2's (512-d × 8 decoder + protections)** | **+0.003 [−0.004, +0.010]**, p 0.20 | **+0.003 [−0.006, +0.011]**, p 0.30 | **FAIL** (max upper +0.012) |

## Motivation

**Why it matters beyond P1.2.** MAE is P1.3's primary vehicle. If MAE does better frozen, P1.3's forgetting study would
be protecting a backbone the deployment should not be training. So P1.2.2 has to settle, before P1.3 starts, whether
some reasonable recipe makes adapted MAE at least match B5.

**The bound that makes it diagnosable.** As the learning rate goes to zero, the adapted encoder *is* B5. So an adapted
encoder that reads clearly below B5 is being moved somewhere harmful. That movement has a cause, and the recipe offers a
short list of suspects.

**The clue from P1.2.1.** MAE has lost 2–3 scene points by step 100, with heads already settled, and then slides slowly.
JE, on the same data and pipeline, gains over the first ~900 steps. Damage that fast points at the optimizer more than
at the data.

## Design

The walk, one seed per arm first, each from a settled-head well (P1.2.1's recipe otherwise). Every arm is read on the
train-side **selection set** (150 + 150 per scene, reserved in P1.2.1's stream, never trained on), at the end of the
drive, on the primary rung (few-shot *k* = 100) and the frozen rungs.

### The suspects and their arms

1. **A pipeline bug — runs first.** A zero-lr drive must leave the encoder bit-identical to B5, and the ladder must read
    Δ = 0 exactly. This certifies the drive → checkpoint → reader path before any arm is interpreted.
1. **The optimizer.**
    - *Learning rate:* ⅓× and 3× the pinned 1e-4.
    - *Warmup* — **added after seeing P1.2.1's Δ(t)**, because of the step-100 loss: a linear warmup over the first 10%
        of the drive, then constant. A fresh AdamW's first steps move every parameter by about the full learning rate,
        whatever its gradient; on a pretrained ViT-B at 1e-4 and batch 32 that is a large jolt. (For scale: the MAE
        paper's scaling rule, 1.5e-4 × batch / 256, gives ~1.9e-5 at batch 32.)
    - *Fine-tuning protections:* layer-wise lr decay (0.75 per block, so early blocks move least), and no weight decay on
        norms, biases and position embeddings. AdamW's decay currently pulls every pretrained weight toward zero.
1. **The decoder.** Ours is 64-d × 2 blocks, sized for the tiny ViT. The arm uses the MAE paper's 512-d × 8 blocks (its
    heads settled the same way). The priors conflict, which makes it a real test:
    - *For:* the MAE paper reports a deeper decoder lifts linear probing by ~8 points, because the encoder's last blocks
        no longer have to specialize in pixel detail.
    - *Against:* [P0.5](../latest-results/P0.5.md) used an over-powered decoder as a lever that *degrades* MAE — the
        decoder does the work, so the encoder does not have to. That was from scratch at toy scale; here the encoder
        starts competent.
1. **Where the probe reads — no new training.** Per-block probes (blocks 4–12, mean-pooled, as
    [`cafl4ds/block_features.py`](../../../cafl4ds/block_features.py) defines them) on P1.2.1's saved checkpoints,
    against B5's blocks. Does adaptation move the useful information off the last layer? This read runs on JE's
    checkpoints too, as a secondary.

Arms 1–3 are six one-seed drives (zero-lr, ⅓×, 3×, warmup, protections, decoder). If two levers each help, their
combination is a seventh arm, decided on the selection set like the others.

### Choosing without forking paths

- **Selection.** The best arm is the one with the highest selection-set few-shot read at the end of its drive. Val is
    not read for any arm.
- **Confirmation.** Only the chosen recipe runs at 5 seeds, and is read once on val against **P1.2.1's bars as written**
    (primary rung few-shot *k* = 100; PASS at one-sided p ≤ 0.025 on either task, Holm over two; FAIL if every rung on
    both tasks rules out a 2-point gain).
- **Outcomes.**
    - *PASS:* MAE keeps its place as P1.3's primary vehicle, with the chosen recipe as P1.3's MAE recipe.
    - *FAIL:* a No-Go for MAE at pretrained init on this horizon. P1.3 is then raised with the user: the recommendation
        would be to make JE its primary vehicle, where P1.2.1 already found a forgetting lead, rather than to halt.
    - *INCONCLUSIVE:* five more seeds of the chosen recipe, read once at 10.
- **Diagnosis whatever the outcome.** Each arm's selection-set result is reported, so the culprit is named even if the
    confirmation fails.

### Engineering

- **An lr schedule in the deploy harness.** The loop already steps an optional scheduler
    ([`cafl4ds/loop.py`](../../../cafl4ds/loop.py)); `run_deploy_harness.py` needs to instantiate one from config
    (`warmup_constant`: linear warmup, then flat).
- **Optimizer parameter groups.** A builder for layer-wise lr decay and a no-decay group (norms, biases, position
    embeddings, `cls` token), selected by config.
- **Selection-set reads in the reader.** `read_adaptation.py` with `pool.kind=selection`: fit on the selection support,
    score on its query.
- **Per-block probes.** A `block` option in the reader that encodes with `block_features` and probes that block.
- Tests on the synthetic source for each; pre-commit clean.

### Cost

Six (or seven) one-seed drives at ~21 min plus their reads (~2.5 h on one card; the decoder arm runs slower), then a
5-seed confirmation and its val ladder (~2.5 h on one card). The per-block read is ~30 min. About 5 h wall across both
cards.

## Results

### The arms and the choice (recorded 2026-10-22, before the confirmation)

**Arm 1, the pipeline check, passes.** After a full 1,748-step drive at lr 0, the whole method is bit-identical to
`wells/p121/mae_heads.pt`: all 152 encoder tensors and every head tensor. On the selection set, its per-image
correctness equals B5's exactly on every rung. So the drive → checkpoint → reader path adds nothing of its own.

**Arms 2–3, one seed each (seed 0), on the selection set** (150 + 150 frames per scene, scene task, end of drive; val
not read). Δ is against B5, with an image-bootstrap 95% interval (one seed, so the interval holds image noise only):

| Arm | ft100 | Δ ft100 vs B5 | Linear | kNN |
| -- | -- | -- | -- | -- |
| B5 (frozen) | 0.630 | — | 0.576 | 0.469 |
| P1.2.1's recipe (lr 1e-4, 64-d × 2 decoder) | 0.563 | −0.067 [−0.099, −0.038] | 0.538 | 0.464 |
| lr ⅓× (3.3e-5) | 0.572 | −0.059 [−0.090, −0.030] | 0.529 | 0.471 |
| lr 3× (3e-4) | 0.539 | −0.092 [−0.127, −0.057] | 0.536 | 0.469 |
| Warmup (10%, then constant) | 0.567 | −0.063 [−0.094, −0.033] | 0.567 | 0.462 |
| Protections (layer decay 0.75, no-decay group) | 0.585 | −0.045 [−0.072, −0.019] | 0.544 | 0.469 |
| 512-d × 8 decoder | 0.616 | −0.014 [−0.039, +0.010] | 0.569 | 0.453 |
| **512-d × 8 decoder + protections** (the combination arm) | **0.623** | −0.007 [−0.029, +0.015] | 0.567 | 0.469 |

The decoder and the protections were the two levers that helped, so their combination ran as the seventh arm, as the
design allows.

**The per-block read** (BDD val, frozen rungs, P1.2.1's five walk-end checkpoints against B5; Δ is the five-seed mean).
On B5, the scene task reads best at block 9 (linear 0.650), not at the output (0.635). MAE's adaptation leaves the early
blocks intact (block 4: +0.001) and costs most in the late blocks (blocks 9–12: −0.042 to −0.048). On the traffic-light
task, MAE's per-block changes are small (−0.011 to +0.025). JE's linear gain sits in the last two blocks (scene +0.017
and +0.027 at blocks 11–12; traffic light +0.031 to +0.048 from block 8 on). JE's scene kNN loss is concentrated at the
top as well (block 12: −0.090).

**What the arms say.** The decoder is the culprit: every arm that keeps P1.2.1's 64-d × 2 decoder reads 4–9 points below
B5, and both arms with the 512-d × 8 decoder close the gap to within noise (see [Interpretation](#interpretation)).

**Choice: the 512-d × 8 decoder + protections** (0.623, the highest read). The confirmation runs it on fresh seeds 1–5,
from its own settled-head well (`wells/p122/mae_dec512_heads.pt`, settled exactly as P1.2.1's), so the seed it was
chosen on is not reused. It is read once on val against P1.2.1's bars as written. On the selection set the recipe sits
just below B5, so a PASS is not expected. What the confirmation decides is whether it is a FAIL (every rung rules out a
2-point gain) or INCONCLUSIVE.

## Interpretation

### The decoder, not the optimizer

P1.2.1's step-100 loss pointed at the optimizer, and the design's warmup arm was added for that reason. The arms say
otherwise. Changing the learning rate (⅓× or 3×), warming up, or protecting the early blocks leaves MAE 4–9 points below
B5 while the 64-d × 2 decoder stays. Swapping in the 512-d × 8 decoder alone recovers most of the gap.

Why this makes sense: MAE's loss reconstructs pixels, and the decoder decides how much of that work the encoder must do.
A tiny decoder cannot turn abstract features into pixels. So the gradient pushes the encoder's last blocks toward
pixel-level detail, away from the semantic features the probes read. The per-block read shows the damage exactly there:
blocks 9–12 lose 4–5 scene points while block 4 is untouched.

**This reverses the prior from [P0.5](../latest-results/P0.5.md).** There, an over-powered decoder was a lever that
*degrades* MAE, because the decoder does the work and the encoder learns little. That was from scratch at toy scale.
Starting from a competent pretrained encoder, the risk runs the other way: an under-powered decoder actively damages it.

### Matching B5 is not beating it

With the decoder fixed, adapted MAE sits at B5 on the primary rung and slightly below it on the frozen rungs (scene kNN
−0.017, few-shot *k* = 10 −0.012, both excluding zero). So one pass over ~56k new frames gives MAE nothing a trained
head can use. The MAE paper's own evidence fits: MAE features are built to be fine-tuned, and the encoder had already
seen ImageNet at a far larger scale. A second pass, a longer horizon or a larger domain shift might change that. None
was tested here.

### What it means for P1.3

The design fixed this outcome in advance: a FAIL is a No-Go for MAE at pretrained init on this horizon, and P1.3's
vehicle is raised with the user. The user has not made that call. A second MAE pass comes first.

What this substudy leaves that pass:

- **One sensitivity found, so others may exist.** Decoder capacity moved MAE by ~5 points; no other lever moved it by
    more than 2. The levers not yet tried include the decoder's size beyond the paper's, the mask ratio, the learning
    rate *with* the large decoder (every lr arm used the small one), and a longer horizon.
- **The fixed recipe is the right baseline.** P1.2.1's recipe damages the encoder for a reason unrelated to the stream,
    so any further MAE work should start from this substudy's recipe.
- **The alternative stays on the table.** JE gains from the stream ([P1.2.1](P1.2.1.md), and [P1.2.4](P1.2.4.md)'s
    confirmation), which is why the design recommended it for P1.3.

## Insights

- **The zero-lr check certifies the pipeline.** A full drive at lr 0 returns the well bit for bit, and the ladder reads
    B5 exactly. Every difference reported here is training.
- **Decoder capacity is an encoder-protection lever for pretrained MAE.** It is the only lever that mattered here, and
    it reverses the from-scratch intuition.
- **The damage lives in the late blocks.** On B5 itself, the scene task reads best at block 9 (linear 0.650), not at the
    output (0.635). JE's linear gain sits in its last two blocks, and so does its kNN loss (block 12: −0.090 on scene).
- **"Not worse" is not "better".** Repairing the recipe removes MAE's loss but adds no gain. For now, leg (a) rests on
    JE.

## How to run

The arms, the combination and the confirmation are three launchers on one card (~1 h for the six arms and their reads,
~25 min for the combination, ~2.2 h for the confirmation). The per-block read is part of
[`artifacts/P1.2.4/run_p124_bdd.sh`](artifacts/P1.2.4/run_p124_bdd.sh). Then the gate, on CPU:

```bash
bash docs/experiments/phase1/artifacts/P1.2.2/run_p122.sh
bash docs/experiments/phase1/artifacts/P1.2.2/run_p122_combo.sh
bash docs/experiments/phase1/artifacts/P1.2.2/run_p122_confirm.sh
uv run python scripts/analyze_adaptation.py mode=p121 root=outputs/p122/confirm 'backbones=[mae]' n_iid_seeds=0
```

The recipe's overrides on `scripts/run_deploy_harness.py`:
`ssl.decoder_dim=512 ssl.decoder_depth=8 ssl.decoder_heads=16 ssl.decoder_mlp_ratio=4.0 param_groups.layer_decay=0.75 param_groups.no_decay=true`,
from a well settled with the same decoder (`scripts/warm_well.py ... warmup.freeze_encoder=true`). The reader needs the
same `ssl.decoder_*` overrides to load its checkpoints.
