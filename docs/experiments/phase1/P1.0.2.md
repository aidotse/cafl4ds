# Deployment-prototype de-risker harness `[engineering]`

The third Phase-1 sub-study (see the [Phase 1 overview](index.md)). P1.0.0 built the open-loop harness and P1.0.1
certified its arm-alignment — but both run on the **toy** substrate (STL-10 / synthetic), which Phase 0 showed is a
smoke-test only. This sub-study takes the certified loop onto the **real substrate the exit gate ultimately stands on**
— BDD100K — as a **deployment prototype**: a concrete, from-scratch-runnable system that streams a realistic driving
diet through a config-selected backbone and logs a Phase-0-informed multivariate health signal, so the real-data
ingestion is de-risked before the mode studies (P1.3 / P1.4) need it.

It is deliberately **engineering only**. It reads **no degradation** — the acceptance bar is that the pipeline *runs as
intended* and the readings are *sensible* (NaN/finite + plausible-range checks), never that they show a pathology. The
diet's scientific adequacy and every degradation read stay with P1.1 / P1.3 / P1.4.

## Motivation

Nothing yet de-risks the substrate the phase's scientific claims live on. STL-10 is a smoke-test by construction — Phase
0 showed it cannot induce forgetting even under a deliberate control, and its low-res / few-class regime *amplifies* the
benign tunnel-effect rank drop — so reading dynamics off it would be an artifact at best. The claims rest on BDD's real
correlation. The catch is that BDD ingestion (a much larger, attribute-rich, real image corpus), a *meaningful* learning
diet over it, and a health-logging path that survives at horizon are all unbuilt — and a null on BDD is only
interpretable as "no coupling" rather than "underpowered / mis-configured" if that apparatus has first been proven to
run and read sensibly. This sub-study builds and validates that apparatus.

A second motivation is hand-off. A deployment prototype is a concrete system others can stand up from a **fresh clone**
and run to extract health-signal traces of their own, on their own configurations — so the sub-study is scoped to be
reproducible from scratch, corpus-first (below), and compute-portable.

## Scope of this slice

**In scope.** A new entry point (`scripts/run_deploy_harness.py` + `deploy.yaml`) that adds, over the P1.0.0 harness:

- The **BDD100K substrate** — a new `DataSource` over the BDD100K *images* (not video) with its metadata attributes.
- A **meaningful, configurable diet** over that substrate, with a proposed default (below).
- A **config-selected backbone** (`backbone=mae|je`, one per invocation) and **optional** PC/B5 gate arms.
- **Phase-0-informed multivariate logging** — the full instrument vector each checkpoint, label-free *and*
    labelled-canary channels, every signal tagged with its Phase-0 calibrated status via a code trust-map registry.
- A **two-tier validation** (below) and an explicit **from-scratch setup**.

**Out of scope** (each has its home):

- **Any degradation number or its interpretation** — P1.3 (forgetting) / P1.4 (collapse).
- **The diet's scientific validation** — whether the diet actually *induces* a pathology is a P1.1 / P1.3 / P1.4
    question; P1.0.2 owns the diet *machinery*, not the verdict.
- **FL and the monitor→filter slow edge** — later phases.

## The four deltas vs. the toy smoke

| Delta | P1.0.0 (toy smoke) | P1.0.2 (deployment prototype) |
| -- | -- | -- |
| **Substrate** | STL-10 / synthetic, in-memory | BDD100K images, disk-backed, attribute-rich |
| **Diet** | synthetic `class_blocked` (label blocks) | attribute-driven era ordering over real BDD metadata (configurable; default below) |
| **Backbone** | swept per cell (`C`) | **config-selected** backbone (`mae` or `je`), one per run; PC/B5 gate arms **optional** |
| **Logging** | directional smoke, one instrument set | full multivariate vector, **label-free + canary** channels, **trust-map** annotated |

`backbone=mae|je` runs **one** backbone per invocation rather than co-stepping the two: a co-step at BDD scale can't
materialize the stream and couples two independent deployments precariously, whereas P1.0.1 certified that the same
config + seed reconstructs the *same* data regime — so two sequential runs are comparable by construction, no co-step
needed.

## The diet — configurable machinery, with a proposed default

Where the toy harness mimics correlation with synthetic label blocks, BDD offers real levers: temporal / regime
correlation and attribute shift over its metadata (`weather`, `scene`, `timeofday`). The harness ships the *machinery* —
attribute-driven era ordering — and one default recipe, and leaves the recipe configurable to explore others.

**The default recipe.** Model a driving stream that is (a) *correlated* — eras are regime blocks keyed on
`(timeofday, weather)`, within-era shuffled; (b) *nonstationary* — eras ordered to walk a shift, e.g.
`daytime·clear → daytime·rain → dawn/dusk → night`; (c) *long-tailed* — rare regimes (foggy, snowy, night) stay rare.
Single pass. The correlation-strength knob is the block granularity — the real-attribute analogue of `class_blocked`'s
`block_size`. This is a *default*, not a certified pathology-inducer.

## Logging — the multivariate signal and its trust map

The monitor already emits the full geometry vector at every surface each checkpoint (`rankme`, `mean_feature_var`,
`offdiag_cov`, `uniformity`, `alignment`, `cka_drift`, `cosine_drift`, plus the `_proj` surface for joint-embedding).
P1.0.2 logs all of it, and adds three things:

- **Labelled signals are first-class.** kNN / linear / BWT / FM probes are logged alongside the label-free vector —
    Phase 1 has no deployment label constraint yet, so there is no reason to withhold ground truth.
- **Two channels.** The **label-free vector** (what a real deployment would have) and a **labelled canary** (ground
    truth, available because we control the BDD eval set — the very thing P0.5 said MAE quality monitoring requires). To
    avoid leakage, the canary probes an attribute *orthogonal* to the diet's ordering axis (eras blocked on
    `(timeofday, weather)` → canary probes `scene`).
- **A trust map.** Each logged signal carries its Phase-0 calibrated status — `calibrated` / `candidate` / `trap` /
    `needs-two-sided-control` / `needs-labels` — per backbone, so a consumer never fuses a known trap (e.g.
    `uniformity_proj`, calibrated to collapse, *mis-signals* on forgetting). The map is a typed code registry
    (`cafl4ds/health_trust.py`), provenance-pinned to the Phase-0 substudy that earned each verdict, unit-tested for
    completeness against the monitor's emitted menu, and **stamped into the artifact header** so the logged traces are
    self-describing without the code.

The **default signal set** follows the Phase-0 per-(backbone × mode) assignment; any signal can be logged or un-logged
via config, so the pipeline stays flexible.

**What this unlocks.** The paired **(label-free vector, labelled canary)** traces make *"predict the canary from the
label-free signals"* a well-posed multivariate time-series problem — a natural downstream analysis this harness
provisions the data for.

## Compute portability

The **core is compute-agnostic**: a single `device` knob (`cpu` / `cuda` / `hpu`) flows through the loop and harness as
today, and the BDD loader yields CPU tensors the loop moves to the device — no hardware branching or `habana` imports in
`cafl4ds/`. Two further levers keep it portable:

- **`img_size` downscales to fit memory.** BDD is natively 1280×720 — far too large to step at any real batch — so the
    loader resizes. This is also the low-memory *portability* lever: downscaling is how a CPU or small-GPU box runs the
    *same* pipeline the Gaudi node runs at full resolution. `img_size` must stay consistent with the backbone's patch
    config (a validated constraint, not a footgun).
- **Hardware stays at the existing edges.** The torch build is selected by the `uv` extra (`--extra cpu` /
    `--extra   cu124`, or the Habana base image for `gaudi`); the only hardware-specific artifacts are
    `docker/gaudi.env.Dockerfile` and `scripts/run_gaudi_dev.sh` (reused unchanged, `-m` mounts `bdd_root`). See
    [developing.md](../../developing.md).

## Methodology — the two-tier validation

P1.0.2 is accepted when both tiers pass. Neither reads a degradation magnitude.

1. **Tier A — the anyone-can-run wiring check.** A fast run on the network-free `data=synthetic` source (or a tiny BDD
    subset) at low resolution and few steps, runnable from a fresh clone with no dataset. It asserts the pipeline is
    *wired*: data loads and eras form per the diet; the selected backbone steps; **every configured signal is present
    at every checkpoint** (channel-completeness); both the label-free and canary channels populate; the trust map is
    complete and stamped; nothing goes non-finite; and memory stays flat over a short extended run (reusing
    `all_finite` / `leak_report`). This is the single command that answers "is it running as intended?".
1. **Tier B — the sanity-of-readings pass.** The default BDD diet at a sane scale, run on real hardware, confirming the
    readings are *plausible* (RankMe in a sane range, drift accumulates, the labelled canary probes above chance, no
    NaNs). Still zero degradation interpretation — the P1.0.0 "harness-validation numbers, not claims" bar, on BDD.

## Setup from scratch

For a fresh clone with nothing else:

1. **Pick the torch build.** `uv sync --group dev --extra cpu` (CPU/CI) or `--extra cu124` (NVIDIA); Gaudi HPUs use the
    Docker image, see [developing.md](../../developing.md).
1. **Get BDD100K.** Download the BDD100K **images** (the 100k-image set — *not* the video) and their attribute labels,
    and arrange them into the canonical layout the loader expects (documented at the loader; images dir + the per-image
    `weather` / `scene` / `timeofday` attribute records).
1. **Point the config at it.** Pass `bdd_root=/abs/path/to/bdd` (an absolute path, mirroring `data_root=/mnt/stl10`; on
    the Gaudi launcher, `-m /abs/path/to/bdd` mounts it at the same path).
1. **Verify, then run.** Run the Tier-A wiring check first (below), then the default diet.

## Artifacts — corpus-first

The **primary deliverable is the config plus the promoted logged-signal corpus** — the health traces from the default
diet (both backbones, label-free + canary channels, the trust map embedded) — not merely a gate verdict. The pipeline is
the *means*: checked in and runnable for other configurations, but the thing a consumer picks up first is the traces and
the exact config that produced them. The corpus is promoted, slimmed, and tracked under `artifacts/P1.0.2/` following
the Phase-0 [promotion policy](../phase0/index.md#artifacts).

## How to run

```bash
# Tier-A wiring check — fresh clone, no dataset needed (fastest):
uv run python scripts/run_deploy_harness.py data=synthetic img_size=32 eval_every=3

# The default BDD diet, joint-embedding backbone:
uv run python scripts/run_deploy_harness.py bdd_root=/abs/path/to/bdd backbone=je

# MAE backbone, downscaled for a low-memory box, gate arms off:
uv run python scripts/run_deploy_harness.py bdd_root=/abs/path/to/bdd backbone=mae img_size=128 gate_arms=false
```

Each run writes its config header, the multivariate health corpus (label-free + canary channels), and the embedded trust
map into its Hydra run dir.
