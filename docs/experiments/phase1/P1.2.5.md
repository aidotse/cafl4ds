# Does the gain survive a strong start, and when does it pay? JE at DINO init, the time-to-payoff curve and a wider task panel `[engineering + new runs]` (P1.2.5)

*Design doc — a stand-in for the detail doc until the runs land. Bars fixed 2026-10-25, before any of this substudy's
data.*

**What this substudy is.** A P1.2 sub-study following [P1.2.4](P1.2.4.md) (see the [Phase 1 overview](index.md)). P1.2's
evidence for leg (a) so far rests on one start: the MAE-pretrained ViT-B, continued with a joint-embedding objective
("MAE-init JE"). That start is weak under linear probes, which flatters any adaptation. P1.2.5 asks the question the
project actually has to answer: **in a correlated driving stream, does continuously adapting the best available start
beat keeping that start frozen — and after how much of the stream?**

## Motivation

**The comparison that matters.** The project's setting is a temporally correlated stream; a deployment cannot opt out of
the correlation. So the main indicator is the correlated walk against the same start frozen, as in [P1.2.1](P1.2.1.md)'s
gate. The shuffled (IID) drive stays as an ablation.

**Why a strong start.** [P1.2.4](P1.2.4.md) found frozen DINO and a frozen supervised ViT-B ahead of the MAE start, most
of all on kNN (by 4–7 points), the read that matters for the selection filter. Adapted MAE-init JE beat frozen DINO on
scene only. A reviewer's first question is whether adaptation still pays when the start is already strong. DINO is a
label-free joint-embedding backbone, the same family as SimSiam. So adapting it stays inside the project's discipline:
no labels, and the joint-embedding health signals apply. It is not a replacement for the project's model classes; it is
a better start for one of them. It also gives a JE result independent of MAE's representation.

**Why a curve, not an end point.** "Is adaptation better?" depends on how much of the stream the model has seen.
P1.2.1's walk overtook the frozen start after roughly 10–15k frames and then plateaued on scene, while traffic light
kept climbing. A deployment needs that curve, and whether more of the same data keeps paying.

**Why more tasks.** Both of P1.2's tasks are narrow. The scene label has three classes and little headroom. The traffic
light is smaller than one 16-pixel patch at 224 px, so that task mostly reads intersection context. Larger objects and a
spatial (per-patch) read test what a driving deployment would use the features for.

**A loose end from P1.2.4.** Its attribution controls were matched to P1.2.1's recipe, not the confirmed protections
recipe whose gain it reports.

## Design

Common to every drive unless stated: BDD100K train, the three canary scenes, 224 px squash, batch 32, one pass (1,748
steps), the P1.2.1 reservations (`stream.well_fraction=0.05`, canary 100 + 100 per cell, selection set 150 + 150 per
scene), heads settled on the frozen encoder first (`warmup.freeze_encoder=true`), so step 0 *is* the frozen start. The
full JE health vector is logged every 25 steps. Reads are on BDD val (the P1.2.1 pool and split), on the readout ladder.

### Part A — The DINO-init gate (primary)

**The start.** DINO ViT-B/16 (`encoder=vit_b16_dino`), continued with the SimSiam objective (`backbone=je`) — "DINO-init
JE". Its frozen floor, **B5-DINO**, is the settled-head well's encoder, bit-identical to the downloaded DINO weights.
Continuing with DINO's own objective (teacher, centring, sharpening) would be more faithful but needs a new SSL method
and recalibrated signals; it is out of scope here and noted as the follow-up if Part A is close.

**The recipe, chosen without reading val.** P1.2.4's protections recipe (layer-wise lr decay 0.75, no weight decay on
norms, biases, position embeddings and tokens) at three learning rates — 1e-5, 3e-5, 9e-5 — one seed each, on the walk.
DINO's features differ from MAE's, so its lr is not assumed. The arm with the best selection-set scene linear read at
the end of the drive is chosen and recorded here before the confirmation.

**The confirmation.** The chosen recipe on the walk × 5 fresh seeds, plus its IID control × 3 (secondary). Checkpoints
at the curve's steps (Part B).

### Part B — The time-to-payoff curve

**Within one pass.** Every confirmation drive (Part A's, and a re-run of P1.2.4's confirmed MAE-init recipe, whose
drives saved only their end) saves checkpoints at steps 100, 219, 437, 874, 1,311 and the end — about 3k, 7k, 14k, 28k,
42k and 56k frames. Each is read on val, frozen rungs (kNN, linear). In a single pass every frame is new, so this is
also the curve over unique frames.

**A second pass.** Three of each init's confirmation seeds continue for a second walk over the same frames (a fresh
optimizer from the pass-1 end state; `resume.checkpoint`, `resume.step=0`). Does repeating the data still pay, or has
the model absorbed what this split offers? New frames (BDD's driving videos) are the larger-horizon test; they belong to
P1.3 and are not run here.

**The caveat this cannot lift.** BDD val has the same distribution as BDD train. The curve measures adapting to a fixed
new domain, not to a stream that keeps shifting; that is P1.3's and Phase 4's question.

### Part C — The wider task panel

**Candidates.** Each is screened before any adapted encoder is read:

- `presence_cell:bus`, `presence_cell:truck`, `presence_cell:pedestrian` — presence, balanced within each scene ×
    time-of-day cell (as the traffic-light task).
- `large_cell:<vehicle>` — a car, bus or truck box covering at least 2% of the frame, cell-balanced: an object several
    patches wide.
- `weather` — clear / rainy / snowy (P1.2.0's runner-up, headroom +0.13).
- **Drivable area** — a per-patch linear probe on patch tokens: is each 16 × 16 patch mostly drivable? Read as
    patch-level balanced accuracy on held-out frames. The one spatial read in the panel.

**The screen** (P1.2.0's method, on the BDD *train* pool with frozen encoders only — no val, no adapted encoder): a task
is eligible if scene + time of day predict it at most 0.60 (overlap) and its headroom (full-label fine-tune ceiling
minus frozen linear) is at least +0.05 on **frozen DINO**, the stronger start. Every eligible task joins the panel, up
to four, in order of headroom. The panel is recorded here before any adapted encoder is read.

### Part D — Attribution under the confirmed MAE-init recipe

P1.2.4's two controls (COCO, Places365; 3 seeds each) and a BDD IID drive (3 seeds), all with P1.2.4's protections
recipe, from P1.2.1's settled-head JE well. Same matching, caches and contrast as P1.2.4. It answers P1.2.4's question
for the recipe it actually reports: can a one-off generic adaptation, then frozen, replace learning on the stream? For
DINO-init, the same controls run **only if Part A passes**.

### Part E — Do the health signals transfer to a DINO start?

The JE signals were re-checked on MAE-init JE in [P1.1](../latest-results/P1.1.md). DINO-init drives are healthy by
construction unless the gate says otherwise, so they are a transfer test: read each DINO-init walk against P1.1.0's
healthy bands with [P1.1.1](P1.1.1.md)'s single-drive rule and report the false-alarm rate per panel. A rate near P1.1's
(~1 in 10) means the bands transfer; much higher means a DINO start needs its own null before P1.3 or P1.4 use it.

### Pass bars (fixed before any of this substudy's data)

Seed × image bootstrap intervals throughout, as P1.2.1; one-sided tests at family-wise 0.05 with Holm.

**A — the DINO-init gate.** P1.2.1's bars as written, with B5-DINO as the floor: primary rung linear, gate tasks scene
and cell-balanced traffic light.

- **PASS** — on at least one gate task, Δ (adapted − B5-DINO) has one-sided p ≤ 0.025 (Holm over two).
- **FAIL** — on both gate tasks, every rung's upper bound is below +0.02.
- **INCONCLUSIVE** — anything else (then five more seeds, read once at 10).

**C — breadth (secondary, reported for both inits).** On each panel task, Δ on the linear rung against the init's own
frozen floor, Holm over the panel. Reported as "gains on *k* of *n* tasks", with the kNN rung beside it. No verdict
hangs on it alone; it qualifies the claim below.

**B — the curve (descriptive, two reads fixed in advance).**

- **Time to payoff** — the first checkpoint whose linear Δ against the frozen floor has its lower bound above zero, per
    task and init.
- **Still rising** — the second pass's end against the first pass's end (paired by seed, two-sample bootstrap):
    one-sided p ≤ 0.05 for a gain.

**D — attribution.** P1.2.4's bars as written, per control; the claim is the weaker of the two.

**E — transfer.** Descriptive; the false-alarm rate per panel against P1.1's.

**The claim P1.2 can make after P1.2.5:**

| DINO-init gate | Breadth (DINO-init) | Claim |
| -- | -- | -- |
| PASS | gains on most panel tasks | **Strong** — adapting the best start tried beats keeping it frozen, broadly |
| PASS | gains on few | **Qualified** — adaptation beats a strong frozen start, on some tasks |
| INCONCLUSIVE / FAIL | — | **Weak** for strong starts — adaptation pays for weak starts (MAE-init) only; raised with the user before P1.3, with the scale caveat (one pass, a fixed domain) |

"Most" means more than half of the panel.

### Engineering

- **Box geometry and drivable area on val.** The val label file on disk has categories but no boxes or polygons.
    Re-fetch the 2018 per-image label release (the one train's labels came from), and regenerate val with `box2d` and
    the drivable-area polygons (`scripts/bdd_legacy_labels.py`, extended). If it cannot be obtained, the `large_cell`
    and drivable-area candidates are dropped before any data.
- **New task labels** in `cafl4ds/adaptation.py`: `large_cell:<categories>:<min_area>` from box areas; the drivable-area
    per-patch target (rasterized polygons pooled to the patch grid) and its patch-token probe in the reader.
- **Checkpoint steps** at the curve's steps (`checkpoint_legs=steps`, exists); the second pass via `resume.checkpoint`
    with `resume.step=0` (exists; check that it replays the full walk).
- **The transfer read** (Part E): P1.1.1's rule applied to a new corpus against P1.1.0's bands.
- **The breadth and curve reads** in `scripts/analyze_adaptation.py` (`mode=p125`).
- Tests on the synthetic source for each; pre-commit clean.

### Cost

About 18 card-hours, ~9 h wall on both cards. Part C's screen ~1 h. Part A: heads + three lr arms ~1 h, confirmation (5
walk + 3 IID) ~3 h, reads ~1.5 h. Part B: the MAE-init re-run with checkpoints ~2 h, second passes (3 + 3) ~2.2 h,
checkpoint reads ~2 h. Part D: 9 drives ~3.3 h, reads ~0.5 h. Plus the label re-fetch and engineering.
