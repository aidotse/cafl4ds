# Loop-integration harness `[engineering]`

The first Phase-1 sub-study (see the [Phase 1 overview](index.md)). Phase 0 left the loop's pieces **scattered** — the
adapting backbone in one place, a separate positive-control script per failure mode, the frozen floor measured only at
run-end. This sub-study consolidates them into **one multi-arm harness** that runs the **live / PC / B5** arms and
co-logs them into a single **canonical `comparison.json`**. It is deliberately **number-free**: the deliverable is that
the rig *runs* — instruments move in the right *direction*, the positive control fires, nothing goes NaN, and a
long-horizon run stays finite with flat memory. Reading those movements *as degradation* is the mode studies' job (P1.3
/ P1.4), not this one's.

## Motivation

Nothing else in Phase 1 runs without one *working open loop*. Every downstream study — the reading protocol (P1.1), the
existential floor (P1.2), the two mode-dynamics studies (P1.3 / P1.4) — reads the health trajectory of a live arm
*against* its gate arms (the per-mode PC and the frozen B5 floor). That comparison is the load-bearing Phase-0 lesson
carried into Phase 1: **a signal is only interpretable against its gate**. So the arms cannot live in three separate
scripts writing three separate artifacts; they have to be one loop, co-logged on a shared step index, under one schema.

The Phase-0 pieces this replaces:

- **B5 measured only at run-end.** `scripts/run_loop.py` snapshots a frozen, init-matched twin *before* any gradient
    step and scores it once at the end (`adaptation_report`). Phase 1 wants the frozen floor logged *beside* the live
    arm over the whole horizon, not just at the finish line.
- **A positive control per mode, each with its own `comparison.json`.** `positive_control.py` (collapse),
    `positive_control_forgetting.py` (forgetting), `positive_control_instability.py` — each builds its arms and writes
    its own artifact with a mode-specific shape. Phase 1 wants the PC *loop-integrated* as one arm among three,
    co-logged with the live and B5 arms into a single artifact whose base is shared across modes.

This is **consolidation plus two specific gaps** (B5 as a co-logged arm; the PC as a loop-integrated, co-logged arm) —
not a build-from-scratch. The loop itself (`cafl4ds/loop.py::StreamingLoop`), the filters (`cafl4ds/filters/`), the
monitor (`cafl4ds/monitor.py`), the per-era probe (`cafl4ds/eval.py::PerEraProbe`), and the collapse-PC mechanism
(SimSiam's `anti_collapse` flag) already exist and are reused untouched; the harness (`cafl4ds/harness.py`) only
orchestrates them into the three co-logged arms and owns the canonical schema.

## Scope of this slice

**In scope.** Assemble the known streaming-SSL harness — the substrate is standard (Purushwalkam's continuous-SSL setup
2022; Memory Storyboard 2025); the novelty is the *coupling*, not the substrate — and add what Phase 0 lacked:

- The **selection filter** and the **health monitor** as first-class loop *components* (Phase 0 ran the loop with the
    B-floor accept-all knob only and read the monitor as a side-channel).
- **PC** and **B5** as **loop-integrated, co-logged arms** rather than a separate script and an end-of-run snapshot.
- The **canonical `comparison.json` base schema** (below): P1.0.0 *owns* it. Later studies extend it with mode-specific
    blocks but can always fall back to the base.

**Out of scope** (each has its home):

- **Any degradation number or its interpretation** — deferred to the mode studies (P1.3 forgetting, P1.4 collapse). The
    smoke reads *direction*, never magnitude.
- **Quantifying same-seed vs shared-iterator divergence** — that owns a number, so it is its own sub-study
    ([P1.0.1](P1.0.1.md)). P1.0.0 builds the co-stepped harness only as the *optional oracle mode* P1.0.1 measures
    against.
- **BDD100K, FL, and the monitor→filter (slow-edge) controller** — later phases; the smoke stays on STL-10 and resampled
    images.

## Architecture — the three arms

The harness runs three arms and aligns them on the shared step index:

| Arm | What it is | Built from |
| -- | -- | -- |
| **live** | The adapting backbone under the base filter — the system under test. | `StreamingLoop.run()`, B-floor / stock knob |
| **PC** | A *manufactured* pathology — the gate that proves the instruments fire. | the collapse manufacture: SimSiam with `anti_collapse=False` (Phase-0's `positive_control.py` mechanism, the cheapest single-pass calibrated fire); per-mode PCs plug into the same slot |
| **B5** | The frozen, init-matched backbone floor — measured only, never stepped. | frozen twin snapshot (as in `run_loop.py`), stamped onto the live grid |

The shipped smoke PC is the **collapse** manufacture because it is Phase-0's cheapest calibrated fire (drop SimSiam's
predictor + stop-gradient and the SSL loss rides to its `-1` constant-solution floor while the projector RankMe craters
— a within-arm fingerprint that needs no matched healthy twin). It is a **fixed control**, deliberately independent of
the live arm's `C`/`I`, so it fires identically in every cell — exactly what the smoke needs (proof the harness's
instrument wiring fires), not a claim about the live method. The heavier per-mode PC scripts (forgetting, …) plug into
the same `pc` arm slot for the mode studies (P1.3 / P1.4).

**"Co-logged" is an *output* property, not simultaneous execution.** The two words describe different axes, and it is
worth separating them because they read as if in tension. *Co-logged* is about the **output**: the three arms' health
series land in **one** `comparison.json` on a **shared step index** (so any downstream reader has live, PC, and B5 side
by side). *Option B* is about the **execution**: **how** those series are produced. The two are compatible — you run the
arms one way and log them the other — and Phase 0 already does exactly this (a PC script runs its arms sequentially,
then merges them post-hoc into one artifact).

**Default execution = Option B (sequential same-seed arms).** This is Phase 0's proven pattern. Each arm is a full
`StreamingLoop.run()` (or, for B5, a frozen measured-only pass), re-seeded from the same `seed` so it reconstructs the
same stream, then the arms are **aligned post-hoc on the shared step index** (the `zip(pc, hc, strict=False)` merge
every Phase-0 PC already uses). The arms run **sequentially, not in parallel**; "co-logged" never meant "co-stepped". B5
is the frozen twin `copy.deepcopy(method)` taken *before* the first gradient step; in the harness it is read every
checkpoint rather than only at run-end.

The `live` and `b5` arms share the step grid *exactly* — B5 is measured only (never stepped) and stamped onto the live
arm's `(step, era)` checkpoints, so the two are index-for-index aligned. The `pc` arm is co-logged in the *same*
artifact under the same schema, but runs its own (multi-epoch) horizon so the collapse fires decisively at the toy
scale; its verdict is a self-contained fingerprint, not a step-for-step contrast against live.

The assumption Option B rests on — that re-seeding reconstructs a *bit-identical* stream and keeps the arms aligned — is
**not verified here**; certifying it is [P1.0.1](P1.0.1.md). The harness records the alignment mode in the artifact
header (`alignment: same_seed`); **building** the shared-iterator co-stepped oracle (Option A: all arms drawn from *one*
stream iterator, provably identical data by construction) and measuring the divergence against it is P1.0.1's job.

**What this goes beyond ([P0.1.0](../phase0/P0.1.0.md)).** P0.1.0's ~30-step harness wired stream + backbone + logged
instruments under the B-floor knob. P1.0.0 adds the **filter** and the **monitor** as components, and PC/B5 as
**loop-integrated baselines** co-logged into one artifact — the coupling P0.1.0 stopped short of.

The component map is P0.1.0's, extended (factor letters `A`, `C`, `F`, `I` from the plan's matrix):

| Component | Module | Role / factor |
| -- | -- | -- |
| Stream | `cafl4ds/data/streams.py` | `EraStream` — `class_blocked` (**F**=correlated) or `iid`; eras + held-out eval |
| SSL method (**C**) | `cafl4ds/ssl/` | MAE / SimSiam; `apply_encoder_init` (**I** = from_scratch / pretrained) |
| Filter (**A**) | `cafl4ds/filters/` | the selection knob — B-floor / reservoir / dedup / loss (stock knobs) |
| Monitor | `cafl4ds/monitor.py` | `HealthMonitor` over the fixed probe set |
| Loop | `cafl4ds/loop.py` | `StreamingLoop` — one arm's run, reused untouched |
| Harness | `cafl4ds/harness.py` | the arms, the alignment grid, the gate, the canonical-schema builder (Hydra-free, unit-tested) |
| Entry point | `scripts/run_harness.py` | Hydra wiring: instantiates the arms, runs the smoke (or the long-horizon check), writes `comparison.json` |

## The canonical `comparison.json` (base schema)

P1.0.0 owns the base schema; the per-mode PC scripts already write variants of it (`{gate, pc, healthy, …}`), and this
unifies them. The base is the *common core* every Phase-1 harness run emits; a study extends it with a mode block
(collapse adds `envelope`, forgetting adds `savings`, …) but a reader can always fall back to the base:

```jsonc
{
  "schema_version": 1,
  "config": { "C": "mae", "I": "from_scratch", "F": "class_blocked", "A": "AcceptAll", "seed": 0, "alignment": "same_seed" },
  "gate":  { "mode": "collapse_smoke", "passed": true, "checks": { ... }, "thresholds": { ... }, "reported": { ... } },
  "arms": {
    "live": { "run_name": "...", "health": [ /* per-(instrument × surface) records over steps */ ] },
    "pc":   { "run_name": "...", "health": [ ... ] },
    "b5":   { "run_name": "...", "health": [ ... ] }
  },
  "directional": { "rankme_responded": true, "drift_accumulated": true, ... },  // live-arm "moved the right way?"
  "finite": true
  // mode extensions live alongside `arms`, e.g. "envelope": { ... } (collapse) or "savings": { ... } (forgetting)
}
```

The `health` record shape is the existing run-log health series (`step`, `era`, and the instrument × surface values —
RankMe, drift, probe, …), so the harness reuses `cafl4ds/run_log.py` unchanged and only adds the `schema_version` /
`config` header, the per-role `arms` map, and the `directional` / `finite` reports. `live` and `b5` carry the **same
step index** (B5 stamped onto the live grid) — the alignment that makes "read movement against the gate" well-defined;
the `pc` arm carries its own (longer) horizon. `SCHEMA_VERSION` is bumped only on a breaking change to this base.

## Methodology — the two acceptance checks

P1.0.0 passes when both checks pass. Neither reads a degradation *magnitude*.

1. **The full 2×2 C×I STL-10 smoke.** Run the harness across MAE / SimSiam × from_scratch / pretrained (the P0.1.0 exit
    matrix), each with the live / PC / B5 arms co-logged. Acceptance is qualitative and directional: the rig **runs**
    end to end; the instruments **move in the right direction** (RankMe responds, drift accumulates — as P0.1.0 already
    showed for the live arm); the **PC fires** (its gate `passed`); and **nothing NaNs** (the loop's non-finite guard
    never trips). No degradation numbers are claimed or interpreted.
1. **The long-horizon leak check.** STL-10 is a handful of batches; a leak or a slow blow-up hides at that horizon. Run
    a **resampled-image** stream (re-sample images to simulate a long horizon — no new data needed) for many more steps
    and confirm the run **stays finite** (no NaN/Inf in loss, grad-norm, or any instrument) with **flat memory** (no
    leak). This is the no-blow-up / no-leak check, not a science run.

Why STL-10 and resampled images, and *only* as a smoke: STL-10 can host the harness but **cannot induce forgetting**
even under a deliberate control ([P0.3](../latest-results/P0.3.md)), and its low-res / few-class regime *amplifies* the
benign tunnel-effect rank drop (Masarczyk 2023) — so it validates the apparatus and nothing more. The scientific claims
live on BDD100K, later.

The harness also runs unchanged on the **network-free `data=synthetic`** source (the substrate `test_loop.py` and the
Phase-0 PC tests use), which stands in for STL-10 in CI and on a machine without the dataset.

## Findings — the C×I smoke passes on STL-10

Ran on real STL-10 at the P0.1.0 exit-matrix settings (tiny ViT, `img_size=32`, 120 img/class, ≤80 train/class,
class-blocked, `eval_every=4`; `I=pretrained` warm-started by an IID pre-pass, `scripts/pretrain.py`). All four corners
pass — the rig runs, the instruments move, the PC fires, nothing NaNs. These are **harness-validation numbers, not
degradation claims** (that reading is P1.3 / P1.4's):

| Cell (C × I) | live RankMe (init → final) | live drift (final cos) | PC gate | finite |
| -- | -- | -- | -- | -- |
| MAE × from_scratch | 7.27 → 2.36 | 0.374 | ✅ fired | ✅ |
| MAE × pretrained | 5.76 → 3.70 | 0.704 | ✅ fired | ✅ |
| SimSiam × from_scratch | 8.58 → 3.45 | 0.358 | ✅ fired | ✅ |
| SimSiam × pretrained | 2.46 → 2.34 | 0.179 | ✅ fired | ✅ |

Three things to read off it:

- **The live arm reproduces P0.1.0 exactly.** Its RankMe trajectories match the P0.1.0 CPU tables cell-for-cell (MAE ×
    from_scratch 7.27 → 2.36, MAE × pretrained 5.76 → 3.70, SimSiam × pretrained 2.46 → 2.34) — because it *is* P0.1.0's
    `StreamingLoop`, reused untouched. The harness adds PC and B5 *beside* it without perturbing it.
- **The PC fires in every cell, identically** (loss floor **−0.993**, projector RankMe **×0.245**). It is the fixed
    manufactured control (seed-0, independent of the live `C`/`I`), so its fire certifies the harness's instrument
    *wiring*, not the live method. On real STL images it rides its −1 constant-solution floor far more decisively than
    on the synthetic blobs (−0.993 vs −0.563).
- **The B5 floor is genuinely frozen** — its RankMe is constant across every checkpoint in every cell (measured only,
    never stepped), the property that makes it a floor.

**One corner in detail — MAE × from_scratch.** Over the 10-era class-blocked STL-10 stream (30 batches, 6 health
checkpoints) the live backbone's RankMe falls 7.27 → 2.36 while cosine drift climbs to 0.374 — the instruments *respond*
to the correlated diet, the P0.1.0 signal now co-logged against its gates. Beside it the frozen B5 twin holds RankMe
flat (the floor), and the collapse PC craters (projector RankMe 15.14 → 3.70, loss floor −0.993). All three arms land in
one `comparison.json` on the shared step index (live and B5 index-for-index; PC on its own horizon), and nothing goes
non-finite.

**The long-horizon leak check passes** — 5 resampled-image passes over one continually-adapting model stay finite with
memory plateauing (RSS 467 → 521 MiB, then flat: tail spread 4.7% < 10%). No blow-up, no leak.

## Artifacts

The harness writes one canonical `comparison.json` (schema above) per run into its gitignored Hydra run dir; the runs
that back the numbers above are promoted under [`artifacts/P1.0.0/`](artifacts/P1.0.0/), following the Phase-0
[promotion policy](../phase0/index.md#artifacts):

- `artifacts/P1.0.0/{mae,simsiam}_{from_scratch,pretrained}.json` — the four C×I cells (`{live, pc, b5}` health series +
    the `collapse_smoke` gate + `directional` + `finite`).
- `artifacts/P1.0.0/long_horizon.json` — the `long_horizon` gate + the per-pass RSS trace (`leak_check`).

The wiring is guarded by `tests/unit/test_harness.py` (the gate, the schema, the finite/leak checks, the alignment grid,
and a light end-to-end over the synthetic arms).

## How to run

The single-run and matrix forms mirror `scripts/run_loop.py`; the harness adds the co-logged PC and B5 arms behind one
command.

```bash
# Fastest network-free smoke (synthetic source), single config:
uv run python scripts/run_harness.py data=synthetic img_size=16 eval_every=3

# The full 2×2 C×I STL-10 smoke (live / PC / B5 co-logged), as a multirun:
uv run python scripts/run_harness.py -m ssl=mae,simsiam init=from_scratch,pretrained

# The long-horizon leak check (resampled-image stream, extended horizon):
uv run python scripts/run_harness.py data=synthetic long_horizon=true
```

Each run writes `comparison.json` into its Hydra run/job dir (resolved via `HydraConfig`, so multirun jobs never
collide). The alignment mode is recorded in the artifact header (`alignment=same_seed`, Option B — the default and only
mode here); the shared-iterator oracle (Option A) is [P1.0.1](P1.0.1.md)'s to build and measure against.
