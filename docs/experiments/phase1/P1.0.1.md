# Arm-alignment divergence — same-seed vs. shared-iterator `[analysis]`

The second Phase-1 sub-study (see the [Phase 1 overview](index.md)). P1.0.0 built the harness on Phase-0's proven
**sequential same-seed arms** (Option B): each arm is re-seeded so it rebuilds "the same" stream, then the arms are
aligned post-hoc by `zip`-ing their step-indexed series. That alignment is inherited by *every* Phase-0 positive control
(`zip(pc, hc, strict=False)` in `positive_control.py`). This sub-study **certifies** the assumption underneath it — that
re-seeding reconstructs a bit-identical stream and keeps the arms in lockstep — against the **shared-iterator oracle**,
and owns the resulting number: the divergence magnitude, decomposed into its two possible sources.

## Motivation

The same-seed pattern rests on one unverified claim: **re-seeding is as good as sharing the data.** If it is not — if
two arms re-seeded from the same value drift apart in the data they see, or in the trajectory they trace on identical
data — then the post-hoc `zip` silently compares arms on *different* streams, and every Phase-0 PC verdict built on that
merge inherits the error. P1.0.0 flagged this explicitly and deferred it here, because certifying it **owns a number**
(the divergence magnitude) and so is a sub-study, not a line in the number-free P1.0.0 smoke.

The clean way to check a reconstruction is against a reference that *cannot* drift. That reference is the
**shared-iterator oracle** (Option A): materialize the stream **once** into a single batch buffer, and have every arm
draw from that same buffer. The data each arm sees is then identical **by construction** — there is nothing left to
assume. Measuring the same-seed harness against this oracle turns "we assume re-seeding is fine" into a measured,
decomposed fact.

## Scope of this slice

**In scope.** Build the shared-iterator oracle as an optional harness mode, and measure the same-seed harness against
it:

- **Data identity** — does a fresh same-seed rebuild reproduce the oracle's batches, pixel for pixel?
- **Trajectory divergence** — does an arm trace the same health trajectory under the same-seed harness as under the
    oracle?
- **Attribution** — split any divergence into **stream construction** (the data half — does the rebuild match?) and
    **in-arm RNG** (the residual on *identical* data — the draws a single arm makes on top of the data: augmentation,
    MAE masking, dropout, BatchNorm).

**Out of scope.** No new backbone, stream, or gate — this reuses P1.0.0's arms and monitor untouched. The oracle is
retained as an *optional* mode; Option B stays the default, now with a certificate behind it.

## Methodology — one arm, four runs, three measurements

A fixed `C × I` arm (the same live-arm build P1.0.0 uses) is run four ways, and three measurements are read off them.
The key enabling fact is that **`EraStream` draws its splits and ordering from its own private `torch.Generator`, never
the global RNG.** Two consequences follow, and together they make the decomposition exact rather than statistical:

1. Re-seeding reconstructs the *same* stream (the private generator is deterministic in the seed) — the data half.
1. Building or materializing a stream **does not consume the global RNG**, so an arm that re-seeds and then trains
    starts its in-arm draws (masking, augmentation) from the *same* global state whether its data was rebuilt or
    materialized — the trajectory half.

The four runs:

| Run | Stream delivery | RNG | Isolates |
| -- | -- | -- | -- |
| **same-seed** | its own freshly-built `EraStream` (Option B) | re-seeded | the Phase-0 default |
| **shared-iterator** | the materialized oracle buffer (Option A) | re-seeded | the reference |
| **in-arm base** | the oracle buffer | re-seeded | a matched twin |
| **in-arm desync** | the oracle buffer | re-seeded **then** `desync_draws` values burned *after* init | the in-arm-RNG lever |

The three measurements:

- **Data identity** = same-seed rebuild vs. the oracle buffer, batch for batch.
- **Matched trajectory divergence** = same-seed arm vs. shared-iterator arm — the actual Phase-0 setting, expected `0`.
- **In-arm desync divergence** = base vs. desync — two arms with **identical init** on the **identical** buffer,
    differing *only* in their in-arm draws (the desync burns RNG *after* init, so init and data stay pinned). This is a
    deliberate control: it isolates the in-arm-RNG contributor and proves the measurement can *see* a divergence when
    one exists.

## Findings — the same-seed `zip` is certified, exactly

Ran on real STL-10 across the P0.1.0 exit matrix (`mae`/`simsiam` × `from_scratch`/`pretrained`, class-blocked, 30-step
stream, 7 health checkpoints). Every cell certifies:

| Cell (C × I) | data identity (rebuild vs oracle) | matched trajectory (same-seed vs oracle) | in-arm desync control (worst gap) |
| -- | -- | -- | -- |
| MAE × from_scratch | bit-identical (0.0 / 30 steps) | 0.0 (all instruments) | 0.045 (`rankme`) — sensitive |
| MAE × pretrained | bit-identical (0.0 / 30 steps) | 0.0 (all instruments) | 0.848 (`rankme`) — sensitive |
| SimSiam × from_scratch | bit-identical (0.0 / 30 steps) | 0.0 (all instruments) | 11.844 (`rankme_proj`) — sensitive |
| SimSiam × pretrained | bit-identical (0.0 / 30 steps) | 0.0 (all instruments) | 5.687 (`rankme_proj`) — sensitive |

Three things to read off it:

- **Stream construction contributes exactly zero.** In every cell the same-seed rebuild is *bit-identical* to the oracle
    buffer (`max_abs_image_diff = 0.0` over all 30 steps). Re-seeding does reconstruct the same stream — as it must,
    since the stream's generator is isolated from everything else. So the `zip` compares arms on the *same* data.
- **The trajectory does not diverge either.** With the data identical and the global RNG left at the seeded state, the
    same-seed arm and the oracle arm trace the *same* health trajectory — `0.0` divergence at every checkpoint, on every
    instrument (RankMe, drift, the VICReg terms, the probes). The whole Option-B pipeline reproduces the oracle exactly,
    not approximately.
- **The measurement is genuinely sensitive — the zero is earned, not vacuous.** The in-arm desync control *does* move
    the trajectory in every cell, so the two preceding zeros reflect a certification, not a blind spot. The magnitude is
    revealing: it is smallest for MAE-from-scratch (0.045 RankMe) and largest for **SimSiam-from-scratch (11.8 projector
    RankMe)** — the projector is SimSiam's collapse-sensitive surface, and its two-view augmentation is a heavier in-arm
    draw than MAE's single mask, so desyncing it in the chaotic from-scratch regime moves the needle hard.

**The insight.** In-arm RNG *is* a real reproduction lever — the desync control makes that concrete — but Phase-0
neutralizes it for free. `positive_control.py` calls `torch.manual_seed(config.seed)` at the **start of each arm**,
which re-synchronizes every in-arm draw to the same sequence. That per-arm re-seed is exactly what drives the
matched-trajectory divergence to zero. The certification is therefore two-layered: the data is safe because the stream
generator is isolated, and the trajectory is safe because the per-arm re-seed re-locks the in-arm draws. Remove either
and the desync column shows what you would pay.

## Recommendation — sequential same-seed stays the default runner

The study earns a concrete disposition: **prefer Phase-0's sequential same-seed arms as the default execution mode, and
keep the shared-iterator oracle as the standing *certificate*, not a production runner.** Three reasons the default
wins:

- **No fidelity is traded.** That is the whole point of the certification above — same-seed reproduces the oracle
    bit-identically, so choosing it costs nothing in accuracy.
- **The arms are independent, so they compose.** Each arm is a standalone `StreamingLoop.run()` that shares no state, so
    you can add a PC variant after the fact without re-running the others, farm the arms across processes or machines,
    and hold only *one* backbone in memory at a time — where co-stepping pins all N models at once. Heterogeneous
    horizons fall out for free (the PC arm already runs a different, multi-epoch horizon than live; co-stepping arms of
    different lengths is awkward, sequential is not).
- **It reuses machinery that already exists.** Sequential same-seed *is* the Phase-0 pattern; the oracle needs a bespoke
    co-step driver — less to build, less to get wrong.

Two caveats keep the oracle worth its place. First, the certificate is **contingent**: it rests on (1) the stream's RNG
being isolated from the global RNG, (2) the per-arm re-seed, and (3) each in-arm step drawing a data/model-**independent
count** of RNG values (so arms with different weights stay in lockstep). A change that breaks any of these — a
per-sample augmentation, a new source that touches the global RNG, GPU nondeterminism — is exactly when the oracle
should be re-run to re-certify. Second, the one place the compute tradeoff could flip is **data-loading cost**:
co-stepping draws the stream *once* and shares it, where sequential re-reads it per arm. Negligible for the in-memory
substrates here, but a disk-bound stream at BDD scale re-read N times could make the shared pass worth it — a Phase-2
consideration, flagged, not decided here. Hence the oracle is retained as an *optional* mode rather than deleted.

## Artifacts

The measurement writes one `divergence.json` per run into its gitignored Hydra run dir; the four cells backing the
numbers above are promoted under [`artifacts/P1.0.1/`](artifacts/P1.0.1/), following the Phase-0
[promotion policy](../phase0/index.md#artifacts). The report is already slim — it carries no per-step health series,
only the three measurements and the decomposition:

- `artifacts/P1.0.1/{mae,simsiam}_{from_scratch,pretrained}.json` — per cell: the `config` header (with
    `alignment: shared_iterator`), the `data_identity` report, the `trajectory.{matched_seed, inarm_rng_desynced}`
    divergence reports (each with `per_surface_max`), the `attribution` split, and the `verdict` (`same_seed_certified`,
    `measurement_sensitive`).

The measurement logic (`data_identity`, `trajectory_divergence`, `build_divergence_report`) lives in
`cafl4ds/harness.py` and is guarded by `tests/unit/test_harness.py` (the identity/divergence math, the report shape and
its certification rule, and a light end-to-end asserting a same-seed arm reproduces the oracle on the synthetic source).

## How to run

The forms mirror `scripts/run_harness.py`; this script adds the oracle and the four-run decomposition behind one
command.

```bash
# The 2x2 C x I STL-10 certification (data identity + trajectory divergence + in-arm control), as a multirun:
uv run python scripts/measure_divergence.py -m ssl=mae,simsiam init=from_scratch,pretrained

# Fastest network-free run (synthetic source), single config:
uv run python scripts/measure_divergence.py data=synthetic img_size=16 eval_every=3
```

Each run writes `divergence.json` into its Hydra run/job dir. `desync_draws` (default `1`) sets how many RNG values the
in-arm control burns after init; any positive count exercises the lever.
